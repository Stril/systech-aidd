# ADR-006: Выбор SQLite как СУБД для персистентного хранения

## Статус
Принято

## Контекст
В рамках спринта SP-1 необходимо реализовать персистентное хранение данных вместо текущего in-memory хранилища (`MemoryStorage`). История диалогов должна сохраняться между перезапусками бота.

Проект включает следующие данные:
- **Users** - пользователи Telegram (user_id, username, first_name, created_at, message_count)
- **Conversations** - диалоги пользователей (user_id, created_at, updated_at)
- **Messages** - история сообщений (id, user_id, role, content, timestamp)

Текущие характеристики проекта:
- Одиночный инстанс Telegram-бота
- Простые CRUD операции
- Линейная структура данных (User → Conversation → Messages)
- Последовательная обработка сообщений
- Принцип KISS (максимальная простота)
- Минимум зависимостей
- Async/await архитектура

## Проблема
Необходимо выбрать СУБД для персистентного хранения данных с учетом:
- Соответствия принципам проекта (KISS, минимум зависимостей)
- Простоты развертывания и поддержки
- Достаточной производительности
- Поддержки async/await
- Возможности локальной разработки
- Легкости бэкапов

## Варианты решения

### Вариант 1: PostgreSQL (отклонен)
Полнофункциональная реляционная СУБД с богатыми возможностями.

**Плюсы:**
- Мощные возможности (полнотекстовый поиск, JSON, расширения)
- Отличная производительность при высокой нагрузке
- Horizontal scaling (несколько инстансов бота)
- Развитая экосистема инструментов
- ACID транзакции высокого уровня
- Поддержка сложных запросов и агрегаций

**Минусы:**
- ❌ Требует отдельного сервера БД
- ❌ Необходим Docker Compose для локальной разработки
- ❌ Дополнительная сложность конфигурации
- ❌ Управление подключениями, пулами
- ❌ Более сложные бэкапы (pg_dump)
- ❌ Оверинжиниринг для текущих требований
- ❌ Противоречит принципу KISS

**Когда был бы оптимален:**
- Несколько инстансов бота (horizontal scaling)
- Высокая нагрузка (тысячи запросов/сек)
- Сложные транзакции и аналитика
- Готовая PostgreSQL инфраструктура в проде

### Вариант 2: SQLite (принят)
Встроенная файловая реляционная СУБД.

**Плюсы:**
- ✅ Нулевая настройка (встроена в Python)
- ✅ Один файл базы данных
- ✅ Не требует отдельного сервера
- ✅ Полностью соответствует принципу KISS
- ✅ Минимальные зависимости (только aiosqlite для async)
- ✅ Достаточная производительность для одиночного бота
- ✅ Простые бэкапы (копирование файла)
- ✅ Отличная поддержка async через aiosqlite
- ✅ Легкая локальная разработка
- ✅ Работает с Docker через volumes
- ✅ Полноценные ACID транзакции
- ✅ Поддержка всех нужных SQL возможностей

**Минусы:**
- ⚠️ Не подходит для horizontal scaling (решается вертикальным)
- ⚠️ Ограниченная concurrent write производительность (для нас не критично)

**Когда оптимален:**
- Одиночный инстанс приложения ✅ (наш случай)
- Последовательная обработка данных ✅ (наш случай)
- Простые CRUD операции ✅ (наш случай)
- Требование простоты развертывания ✅ (наш случай)

### Вариант 3: MongoDB / NoSQL (отклонен)
Document-oriented NoSQL база данных.

**Плюсы:**
- Гибкая схема данных
- Хорошая горизонтальная масштабируемость

**Минусы:**
- ❌ Требует отдельного сервера
- ❌ Избыточна для простых реляционных данных
- ❌ Дополнительная зависимость (pymongo/motor)
- ❌ Наши данные чисто реляционные
- ❌ Оверинжиниринг для проекта

## Решение
Принят **Вариант 2: SQLite** с поддержкой async через `aiosqlite`.

### Обоснование

#### 1. Полное соответствие принципу KISS
- Встроена в Python - нулевая настройка
- Один файл БД - простота бэкапов и миграций
- Не требует инфраструктуры (серверов, Docker для разработки)

#### 2. Минимальные зависимости
```toml
[dependencies]
aiosqlite = "^0.19.0"  # ТОЛЬКО ЭТО!
```
Никаких драйверов, серверов, дополнительных инструментов.

#### 3. Достаточная производительность
Для нашего случая (одиночный бот, последовательная обработка):
- SQLite справляется с десятками тысяч операций в секунду
- Наша нагрузка на порядки ниже
- Write operations последовательные (один пользователь → одно сообщение)

#### 4. Простота разработки и деплоя

**Локальная разработка:**
```bash
make run  # Бот создает bot.db локально - готово!
```

**Docker деплой (опционально):**
```yaml
# docker-compose.yml
volumes:
  - ./data/bot.db:/app/data/bot.db  # Персистентность
```

**Бэкапы:**
```bash
cp data/bot.db data/bot.db.backup  # Готово!
```

#### 5. Полная функциональность SQL
SQLite поддерживает все необходимое:
- ACID транзакции
- Foreign keys и constraints
- Indexes для производительности
- Triggers (если понадобятся)
- Views и aggregations
- JSON поддержка (если понадобится)

#### 6. Отличная async поддержка
```python
import aiosqlite

async with aiosqlite.connect("bot.db") as db:
    await db.execute("INSERT INTO users (...) VALUES (...)")
    await db.commit()
```

#### 7. Гибридный подход разработки
- **Dev**: Локально без Docker - быстро и просто
- **Prod**: С Docker через volumes - изоляция и деплой

#### 8. Возможность миграции
Если проект вырастет и понадобится PostgreSQL:
- Интерфейс `Storage` остается тем же (Dependency Injection)
- Просто меняется реализация
- Данные экспортируются из SQLite в PostgreSQL
- Остальной код не меняется

## Последствия

### Положительные
- ✅ Максимальная простота развертывания (нулевая настройка)
- ✅ Минимум зависимостей (только aiosqlite)
- ✅ Быстрая локальная разработка
- ✅ Простые бэкапы (копирование файла)
- ✅ Полная async поддержка
- ✅ Достаточная производительность
- ✅ Работает с Docker через volumes
- ✅ Соответствие принципу KISS
- ✅ Легкое тестирование (in-memory SQLite для тестов)

### Отрицательные
- ⚠️ Не подходит для horizontal scaling
  - *Решение*: Для scaling можно перейти на PostgreSQL позже
- ⚠️ Ограничения concurrent writes
  - *Не критично*: У нас последовательная обработка

### Нейтральные
- 📝 Один файл БД (может быть плюсом и минусом)
- 📝 Локальное хранилище (файл на диске)
- 📝 Возможность миграции на PostgreSQL в будущем

## Альтернативы, которые были рассмотрены
- **PostgreSQL** - отклонен как избыточный для текущих требований
- **MySQL/MariaDB** - отклонен, похож на PostgreSQL по сложности
- **MongoDB** - отклонен, NoSQL избыточен для реляционных данных
- **Redis** - отклонен, не подходит для персистентного хранения
- **Plain JSON файлы** - отклонен, нет транзакций и индексов

## План миграции с MemoryStorage
1. Создать `SQLiteStorage` с тем же интерфейсом
2. Реализовать систему миграций
3. Написать тесты для `SQLiteStorage`
4. Заменить `MemoryStorage` → `SQLiteStorage` в `main.py`
5. Обновить документацию
