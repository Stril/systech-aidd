## Описание спринтов

### SP-0: MVP и Foundation (✅ Завершено)

**Период выполнения:** 10.10.2025 - 16.10.2025

**Цель:**
Создать полноценный MVP LLM Telegram-бота со специализированной ролевой моделью, качественной архитектурой и высоким покрытием тестами.

**Ключевые достижения:**
- ✅ Полнофункциональный Telegram-бот с командами `/start`, `/help`, `/role`, `/reset`
- ✅ Интеграция с LLM через OpenRouter (поддержка различных моделей)
- ✅ Ролевая модель - системный промпт из файла, команда `/role`
- ✅ Управление контекстом (последние 10 сообщений)
- ✅ In-memory хранилище для пользователей и диалогов
- ✅ Структурированное логирование (файлы по дням, формат с разделителем `|`)
- ✅ Автоматизация качества: ruff (линтер/форматтер), mypy (strict mode)
- ✅ Чистая архитектура: 1 класс = 1 файл, SOLID, DRY
- ✅ Async/await архитектура с run_in_executor для OpenAI
- ✅ Высокое покрытие тестами: 121 тест, 98.12% coverage
- ✅ Unit, integration и property-based тесты (hypothesis)
- ✅ Примеры ролей для различных специализаций
- ✅ Полная документация и guides

**Технологический стек:**
- Python 3.11+, uv для зависимостей
- aiogram (Telegram Bot API)
- openai client + OpenRouter
- structlog (логирование)
- pytest + hypothesis (тестирование)
- ruff + mypy (качество кода)

**Итоги:**
Проект готов к продуктивному использованию. Создана прочная основа для дальнейшего развития с фокусом на качество кода, тестируемость и простоту архитектуры.

### SP-1: Персистентное хранение данных ✅ (Завершено: 16 октября 2025)

**Цель:** ✅
Реализовать сохранение истории диалогов в базе данных вместо текущего in-memory хранения. История диалогов сохраняется между перезапусками бота.

**Ключевые задачи:**
1. ✅ **Анализ требований** - Изучена текущая модель данных и операции
2. ✅ **Выбор технологий** - SQLite, SQLAlchemy, Alembic, оформлено через ADR
   - [ADR-006: Выбор SQLite](adrs/adr-006-sqlite-database-choice.md)
   - [ADR-007: SQLAlchemy ORM + Alembic](adrs/adr-007-sqlalchemy-alembic.md)
3. ✅ **Docker окружение** - Настроен Dockerfile, docker-compose.yml
4. ✅ **Проектирование схемы** - Созданы таблицы users, conversations, messages с индексами и soft delete
5. ✅ **Система миграций** - Внедрен Alembic с автоматической генерацией миграций
6. ✅ **Data Access Layer** - Разработан SQLiteStorage с полной async поддержкой
7. ✅ **Рефакторинг** - Заменен MemoryStorage на SQLiteStorage в main.py

**Реализованные возможности:**
- ✅ Персистентное хранение пользователей, диалогов и сообщений
- ✅ Soft delete стратегия (deleted_at timestamp)
- ✅ Метаданные сообщений (created_at, content_length)
- ✅ Поддержка множественных диалогов на пользователя
- ✅ Natural key (Telegram user_id как PK)
- ✅ Foreign keys для целостности данных
- ✅ Индексы для оптимизации запросов
- ✅ Graceful shutdown с закрытием соединений

**Достигнутые результаты:**
- ✅ История диалогов сохраняется между перезапусками
- ✅ Документированные архитектурные решения (ADR-006, ADR-007)
- ✅ Система миграций Alembic
- ✅ Интеграционные тесты (138 тестов, 100% success)
- ✅ Docker окружение для локальной разработки
- ✅ Coverage: 98%+

**Технический стек:**
- SQLite 3 (файловая БД)
- SQLAlchemy 2.0+ (async ORM)
- Alembic (миграции)
- aiosqlite (async драйвер)
- Docker + docker-compose

**Ограничения соблюдены:**
- ✅ Принцип "1 класс = 1 файл" (database_models.py, sqlite_storage.py)
- ✅ Async/await архитектура
- ✅ Coverage >= 80% (факт: 98%+)
- ✅ KISS principle (простая реализация без оверинжиниринга)

### SP-3: Сохранение информации по диалогу ✅ (Завершено: 16 октября 2025)

**Цель:** ✅
Реализовать восстановление контекста диалога из БД после перезапуска приложения. Теперь пользователь может продолжить диалог с того места, где остановился.

**Ключевые задачи:**
1. ✅ **Анализ требований** - Изучена текущая архитектура ContextManager и Storage
2. ✅ **Проектирование решения** - Выбрана ленивая загрузка контекста при первом сообщении
3. ✅ **Разработка ContextManager.load_context()** - Метод для загрузки контекста из списка сообщений
4. ✅ **Разработка MessageHandler._restore_context_if_needed()** - Приватный метод для восстановления контекста
5. ✅ **Тестирование** - Unit тесты для load_context(), integration тест для восстановления после перезапуска

**Реализованные возможности:**
- ✅ Ленивая загрузка контекста из БД при первом сообщении пользователя
- ✅ Автоматическое восстановление последних N сообщений (по умолчанию 10)
- ✅ Прозрачная работа - пользователь не замечает перезапуска
- ✅ Совместимость с MemoryStorage и SQLiteStorage
- ✅ Логирование восстановления контекста

**Достигнутые результаты:**
- ✅ Контекст диалога сохраняется между перезапусками
- ✅ KISS принцип - минимальные изменения, простое решение
- ✅ Новые тесты (5 unit + 1 integration): 153 теста, 100% success
- ✅ Coverage: 98.56% (было 98.12%)
- ✅ Все проверки качества пройдены (ruff, mypy, pytest)

**Технические детали:**
- Метод `ContextManager.load_context()` - загрузка контекста из списка
- Метод `MessageHandler._restore_context_if_needed()` - проверка и восстановление
- Обновлен `MemoryStorage.get_conversation()` до async для единообразия API

**Ограничения соблюдены:**
- ✅ KISS принцип (простое решение без оверинжиниринга)
- ✅ Принцип "1 класс = 1 файл"
- ✅ Async/await архитектура
- ✅ Coverage >= 80% (факт: 98.56%)
- ✅ Cyclomatic complexity <= 15
